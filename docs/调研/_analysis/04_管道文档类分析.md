**A2. `rules/cleaning_rules.yaml` 新增 `dedup` 规则组 —— 问题2**

**A4. 新增 `cleaner/fuzzy_align.py` —— 移植 LCS 模糊对齐**（问题2/4 共用算法蓝本）

**A5. `clean_batch.py` 加「时间戳间隙切段」** —— 问题1 的工程细节
- 相邻段间隔 >1.5s 视为新段落，防止场景碎句并进下一段。
- 来源：NeMo Curator(§8补丁1)、VideoCaptioner(`_group_by_time_gaps`)、cocoindex(`paragraph_gap_seconds: 1.5`)。

**A6. `rules/cleaning_rules.yaml` 新增 `short_line_classifier` —— 问题3 多特征打分类**
- 特征组合：行长度 + 是否标点收尾 + 是否含数字/公式 + 前后行关系 + 行首模式 + 相邻行重复度。
- 来源：DPK doc_quality 特征清单(bullet_point_ratio/ellipsis_line_ratio/mean_word_len/alphabet_word_ratio，Gopher 论文背书)、dedoc(§8补丁 行特征分类)、unstructured(is_possible_narrative_text + auto_paragraph_grouper)、opendataloader-pdf(§8补丁2 多特征方法论)。

**A7. 新增 `cleaner/llm_correction.py`（可选，默认关）—— 问题4 强解形态**（Stage3.5，插在规则后、校验前）

- 来源：VideoCaptioner(补丁A agent_loop，3星)、docetl(§8 P4 llm_fixer + validation_rules + token 预算上限)、marker(§8补丁2 低置信度才触发)、NeMo Curator(§8补丁3 LLM-as-stage + YAML prompt 模板)。
- 注意：VideoCaptioner 是 **GPL-3.0**，prompt 必须重写为中文语境、自写实现，不得复制原文。

**A8. `cleaner/` 加「可疑行标记」校验器 —— 先打标不自动改**
- 正则特征（`\b\w \w \w\b` 字母间空格、异常字符密度）标记可疑行 + 输出置信度，进人工/复核清单。

## D. 我们项目没有的优点（工程/架构层面缺什么）

1. **结构化数据模型贯穿全链**（mage/tenzir/cocoindex/FunASR/VideoCaptioner）—— 我们的 `clean_text(raw: str) -> str` 是纯字符串函数链，没有「句块对象」中间表示。这是问题1 的架构根因。
2. **声明式阶段表/算子链**（tenzir/vector/ploomber/mage）—— Stage0-5 顺序硬编码在 `clean_text` 函数体内（cleaning.py L493-508），不是可配置阶段。
3. **中间产物落盘 + 单 Stage 回归测试**（mage/ploomber）—— 我们只有最终 txt + meta.json，无法定位"哪一步引入问题"。
4. **LLM 校验重试循环**（VideoCaptioner/docetl/marker）—— 引擎纯确定性，无纠错 stage。
5. **词级置信度/可疑行标记**（surya/dedoc）—— `validate_schema` 只验结构（{ok,text,engine,stats}），无内容级标注。
6. **时间戳元数据保留**（FunASR/VideoCaptioner/NeMo Curator）—— 我们 video_asr 把 segments 拍平，start/end 全丢。
7. **行为级回归测试**（vector 配置带 tests）—— 我们有 jsonschema 结构校验，但没有"输入样例→期望输出"用例。
8. **先打标后过滤**（DPK/Curator）—— 我们规则只有"删行"动作，无"打标行"中间态。
9. **并发背压**（pypeln maxsize）—— `Pool(parallel)` 无有界队列限流。
10. **LLM 调用的工程鲁棒件**（VideoCaptioner diskcache+json-repair、markpdfdown RETRY_TIMES+退避、docetl checkpoint）—— 我们暂无 LLM 调用路径，若有必须配套。

## E. 我们项目已有的缺点（对照暴露出的）

1. **问题1 根因：入口即拍平** —— `clean_text` 接收 raw 字符串，video_asr json 被拼成长段再走字符串规则。cocoindex/FunASR/VideoCaptioner/mage/tenzir 明确点名这是反模式。
2. **去重仅精确行级** —— cleaning.py L303/L336 只有「整行重复≥3次」精确去重，缺模糊/近似去重。VideoCaptioner 报告明确提到这一点。
3. **短行判定是单一长度阈值** —— `_is_watermark_candidate` 用 ≤12 字符单规则（L239），问题3 需要多特征打分（DPK/dedoc/unstructured 一致指出）。
4. **校验层只验结构** —— `validate_schema`(L402) 无内容级检查，surya/dedoc 的「可疑行/低置信词标记」缺失。
5. **规则 YAML 是扁平列表** —— noise_substr/noise_regex 是子串/正则列表，mage data_cleaner 的「动作+参数」结构表达力更强。
6. **缺单 Stage 可观测** —— clean_batch 只输出最终结果，ploomber/airflow 强调的分步日志缺失。
7. **并行无背压** —— Pool(parallel) 无 maxsize（pypeln 指出）。

## F. 我们该避免的错误（含合规风险）

1. **不引入任何编排/解析框架本体** —— ploomber(169万行)/mage(服务+UI+DB)/airflow(Windows 官方不支持+常驻调度器)/prefect(server+DB)/dagster(webserver+GraphQL)/vector(Rust)/tenzir(C++)/cocoindex(Rust内核+向量库)/airbyte(Docker平台)/pathway(BSL)/NeMo Curator(GPU+Ray)/DPK(Ray+Parquet+Rust) 全部 2 星「借鉴思想、不引入」。22/28 家报告明确写了"不引入依赖"。
2. **开源许可红线**：pathway 是 BSL 1.1（非 OSI 开源、禁派生修改、我们 Windows 不原生支持）——绝不能碰；airbyte 是 ELv2（限制托管服务，开源发布有法律负担）；VideoCaptioner 是 GPL-3.0（复制源码/prompt 原文有传染风险，我们项目已发布 GitHub，只搬思路、自写实现）。
3. **不为单文档去重引入文档级去重栈** —— DPK ededup/fdedup、Curator MinHash LSH、cocoindex entity_resolution 全是文档级/图谱级，对「单文档内段落重复」是重炮打蚊子（三仓库自述）。
4. **不为借 1-2 个算法引入 GPU/模型重栈** —— MinerU(20GB模型)/marker(PyTorch+surya)/DeepSeek-OCR(6.7GB+GPU)/surya(vllm+llama.cpp) 均「只读思路」。surya 报告给了 <1 天实测方案（先跑 OCRErrorPredictor 验证再决定）。
5. **停更/半死库不引入** —— pypeln(3年无更新/35 issues)、zerox(停更15个月)、DeepSeek-OCR(已被 OCR2 取代)。作为长期运行时依赖风险大于收益。
6. **批量 LLM 付费失控** —— docetl(成本4星)/zerox(成本1星)/markpdfdown(成本5星) 警示：上 LLM 必须默认关、走 diskcache 缓存、限定来源（仅 video_asr/video_ocr）、设 token 预算上限、低置信度才触发（marker 的成本控制思想）。

## G. 可借鉴的技术栈改进

- **增量策略**：我们已有「文件哈希+规则指纹」增量（clean_batch.py L150-179，等价 ploomber/cocoindex/prefect 思想）。升级点：指纹升级为三元组（清洗器版本号 + 规则指纹 + 输入哈希）—— 对应 cocoindex「代码变→依赖该代码的记录重跑」。
- **缓存机制**：VideoCaptioner 用 diskcache 缓存 ASR/LLM 结果；docetl 有结果缓存+成本追踪。→ 若上 LLM 纠错 stage，clean_batch 加「输入指纹→结果」进程级缓存。
- **编排框架结论**：全部 2 星借鉴、不引框架。自研 ~50-200 行即可覆盖：产物校验（ploomber）、幂等+重试（airflow，已实现 `_clean_one` 重试3次）、断点续跑（已实现 `_clean_state.json`）、数据感知触发（airflow Datasets → 可加 watchdog 监听新转写落地）。
- **并发**：pypeln 的 workers+maxsize 背压 → 批量加大时用 `Queue(maxsize=N)` 限流（标准库即可）。

## H. 与我们有冲突、需评估是否重构的

1. **声明式算子链 vs 轻量规则引擎（冲突程度：中，值得做）** —— tenzir/vector/ploomber 的配置驱动 DAG 与我们的定位部分冲突。**理由**：我们已是「规则数据化」，但执行顺序仍硬编码在 `clean_text`。**值得重构**：改为阶段表驱动 `[_EXTRACT, _NORMALIZE, _RULES, _VALIDATE, _DESENSITIZE]`，中间表示从 str 升级为「句块列表」。这是问题1/2 的架构前提，投入 ~100-200 行，不引框架。
2. **LLM 纠错 stage vs 零成本规则引擎（冲突程度：高，值得做可选层）** —— VideoCaptioner(3星)/docetl/marker/NeMo Curator 的 LLM 词级纠错与我们的「纯确定性、零 LLM 成本」定位冲突。**理由**：问题4 的强解需要它，但批量场景不能常开。**值得做**：默认关、仅 video_asr/video_ocr 来源、走我们已有模型路由（GLM 桥接）、diskcache 缓存、token 预算上限。形态照 NeMo Curator「LLM 作为清洗 stage + YAML prompt 模板驱动」。
3. **结构保留 vs 现有字符串函数链（冲突程度：高，必须重构）** —— mage/tenzir/cocoindex 的「结构化对象流动」与我们 `clean_text(raw:str)->str` 冲突。**必须重构**：入口改为消费 ASR JSON 对象（segments 列表），清洗阶段处理「句块列表」，输出才拼字符串。12 家报告共同背书，是问题1 的唯一正解。
4. **可暂不重构的**：pandas DataFrame 表型中间态（PyFunctional/DPK/Curator）—— 我们处理量级不需要；文档级去重（DPK/Curator MinHash）—— 单文档内去重用 n-gram/SimHash 即可。
